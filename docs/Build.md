- **Real gotcha, cost real time this session: Workers-with-static-assets skips the Worker script entirely by default.** `run_worker_first` defaults to `false`, meaning asset requests (basically every request on a static site) get served directly without ever invoking `src/index.js` — so security-header code silently did nothing until `"run_worker_first": true` was added under `assets` in `wrangler.jsonc`. If a future change to `src/index.js` doesn't seem to take effect, check this first.
- **`CF-Cache-Status` header is unreliable for debugging** per Cloudflare's own docs — it's probabilistically included for privacy reasons, don't trust it when checking whether a deploy went live. Use a real content check (grep the response body/headers for what actually changed) instead, and if it looks stale, just poll for ~30-60s — new deploys and newly-registered `workers.dev` subdomains both showed a real propagation delay this session (one appeared as a TLS handshake failure for about a minute after first registering).
- **Custom Domains, not DNS CNAMEs, point comprsly.com at the Worker.** `wrangler.jsonc`'s `routes` array has `{"pattern": "comprsly.com", "custom_domain": true}` (and the same for `www`). Cloudflare will refuse to create a Custom Domain on a hostname that still has a CNAME record — the old Tunnel CNAMEs for `comprsly.com`/`www.comprsly.com` (type "Tunnel" in the dashboard, pointing at the "wordpress" tunnel) had to be manually deleted in the DNS Records page first, `wrangler deploy` doesn't have permission to do that itself (the OAuth token only grants `zone:read`, not DNS edit).

## 4. How it works

### Text detection (the core)
`watch_loop` polls every 0.7s. It reads the **focused control** and activates wherever there's a readable text field. The focused control *is* the active chat box, so only that box is ever analysed.

**An empty box is not empty to UI Automation.** The placeholder is part of the accessible tree, so `get_focused_text()` happily returned Claude's `"Type / for commands"`. Comprsly analysed it (correctly finding no grammar issues) and then fed it to the AI, which faithfully compressed a placeholder from 4 tokens to 5. From outside that reads as "grammar found nothing and the AI did nothing", which is exactly how Antonio reported it. There is no reliable accessibility flag for this, so `PLACEHOLDER_TEXTS` is a known-strings list, matched exactly after stripping so it can never swallow real typing. Add to it when a new app shows up.

Reading order in `get_focused_text()`:
1. `ValuePattern` — plain textarea/input/native edit
2. `TextPattern` — contenteditable and rich composers (Claude, most chat UIs)

Both are fetched via `_safe_pattern()` using **generic** `control.GetPattern(PatternId.X)`. This is critical, see §6.

| Surface | Read | Write |
|---|---|---|
| Chrome | ✅ | ✅ ValuePattern.SetValue |
| Edge | ✅ | ✅ |
| Native Windows apps | ✅ | ✅ |
| Claude desktop (Electron) | ✅ TextPattern | ❌ → clipboard paste fallback |

Fallback chain when UIA gives nothing: keystroke-reconstruction buffer (a `WH_KEYBOARD_LL` hook), then a one-time clipboard read on explicit click.

### The two-step flow
1. **Step 1 — Fix Grammar & Clarity.** Rules apply instantly and visibly. User sees the cleaned text.
2. **Step 2 — Make It Concise.** AI compresses the *already-corrected* text (so it reads "output", never "putput"). Result is **previewed with Apply/Dismiss**, never auto-pasted.

Rules always run first and hand clean input to the AI. Neither overrides the other.

### Rules engine (`suggestion_engine.py`)
Span-based (real start/end offsets), per-occurrence, individually acceptable.

- Spelling via `winspell` (native Windows COM spell-check)
- **Misplaced spaces** (`_find_misplaced_space_suggestions`, added 2026-07-21). `"lik ethis"` → `"like this"`, `"tak eto"` → `"take to"`. See below, this one is subtle.
- Grammar: repeated words, missing space after punctuation, a/an, lowercase standalone `i`
- Wordiness: filler phrases, verbose phrases, repeated instructions
- **Content protection**: URLs, numbers, code (inline + fenced), shell commands, likely proper nouns, markdown structure. Every rule checks `_overlaps_any()` before firing.

### Apply, and where it writes (rewritten 2026-07-21)

Apply used to ask "what control has focus right now?" That is the wrong question, because by then the thing with focus is Comprsly's own popup button. Two real failures came from it: the direct UIA write path was skipped even where it would have worked, and the clipboard fallback sent `Ctrl+A` into a window whose composer no longer held focus, which in Claude selects the **entire page**.

The control is now captured at badge-click time and threaded through. Order of attempts:

1. `SetValue` on the **captured** control. No clipboard, no keystrokes, no focus fight.
2. Otherwise `restore_field_focus()` before anything else: force foreground → `SetFocus()` on the captured control → verify by reading the focused control back and checking it still ends with the text we analysed → if that fails, click back at the user's own last click point (only if it's still inside the target window) → verify again.
3. Only with focus confirmed (or confirmed-unverifiable after a real click back into the field) does `Ctrl+A`/`Ctrl+V` fire. **If focus can't be established, Apply refuses and says so, rather than selecting something at random.**
4. After the paste, the field is read back and `paste_landed=yes/NO/unreadable` goes in `debug.log`. Past "Apply does nothing" rounds were slow precisely because the success line only proved the function didn't raise.

### UI (rewritten 2026-07-24 — see §10j for the full decision trail)

**Two UI surfaces, deliberately on two different stacks, and that split is final, not a migration in progress:**

- **Settings and Onboarding are a real web UI** — WebView2 via `pywebview`, running as their own subprocess (`main.py --web-settings` / `--onboarding`), talking to the real Python engine through a `Bridge` js_api in `webui.py` (`get_state`/`set_setting`/`set_theme`/`download_model`/`delete_model`/`open_acknowledgements`/`reveal_installer`/…). HTML lives in `webui/settings.html` and `webui/onboarding.html`, Deep Iris design tokens, light+dark. This works well and was the right call for these two surfaces — they're not floating overlays, so being a real window is fine.
- **The badge and the review card are native Tkinter, and this is the final decision, tried both ways.** A persistent, always-warm WebView2 review card (`webui.py --review-card-server`, `main.py`'s `WarmReviewCard`) was fully built and made to work technically — instant show, correct position, no focus-steal, matched the HTML mockup pixel-for-pixel. Antonio rejected it anyway: it's a real OS window, which lights up the taskbar and reads as "a window popped up" rather than an overlay, and that's true of *any* WebView2 card regardless of how well it's tuned. The warm-server code is kept in the tree, dormant (`warmcard.launch()` is commented out in `main()`), in case it's ever revisited, but the shipped path is `_show_tk_card()` unconditionally.

**Badge** (`PersistentBadge` in `main.py`): teardrop mark with its own silhouette filled dark (`assets/badge.png`), never on a square tile (see §6). **Not draggable** — auto-anchors to the left of whatever text box is focused, every time, no exceptions, no pin/park state (an earlier drag-to-pin experiment was explicitly reversed — "we never wanted it draggable anywhere"). A click opens the review card. While the card is open the badge stays visible and on top (`raise_to_front`), nested into the card's bottom-right corner with a **see-through gap ring punched around it** (`_punch_gap`, colour-keyed transparent disc, `-transparentcolor` on the card window) so the badge reads as docked rather than embedded.

**Review card** (`SuggestionPopup` in `main.py`), theme-adaptive Deep Iris palette (`_apply_card_palette`, follows System/Light/Dark live — polls the settings file each watch-loop tick so a Settings toggle applies to an already-open card within ~0.7s, see `retheme()`):
- Header: brand mark (swaps asset per theme so the "C/" stays legible on both — `_load_logo_image` on dark, `_load_badge_mark_image` on light), a green "On your device" pill, a **settings gear** (`_draw_header_gear`, hover recolors muted→violet), and the ✕ close, in that visual order.
- Clicking the gear runs `SuggestionPopup._trigger_settings()`: a 7-step ease-out slide-down of the card, then `dismiss()` + the same `open_settings` the tray menu uses. (This lived on the badge itself in v0.9.43 for about one build; Antonio corrected it immediately — "I wanted it in the ui that pops up, not on the badge" — and it moved to the card header, where it's stayed since.)
- Step 1's fix list is a fixed-height canvas that caps at **3 visible rows** with a custom violet pill scrollbar drawn on a second canvas (`_build_fixlist`) — Tk's real `Scrollbar` ignores `troughcolor` on Windows and draws a native white/grey bar, which is why this is hand-drawn instead.
- **The list live-updates while the user keeps typing** (`refresh()` → `_sync_fixrows`): new fixes are appended as individual rows, existing rows and checkbox states are left untouched, and the card only resizes while still under the 3-row cap — a full rebuild (which used to flash the whole card white for a frame) only happens on a structural change (list appears/disappears, AI availability flips).
- Each fix's checkbox default reflects its **confidence tier** (see §10j) — Tier 1/2 (safe) start checked, Tier 3 (judgment calls: homophones, stylistic punctuation, style trims) start unchecked — so a bulk "Apply N fixes" only ever applies what's genuinely safe, and the button label tracks the *ticked* count live, not the total found.
- **The card progresses in place, it is never rebuilt mid-flow** (real ask 2026-07-21, still true). Each step lives in its own container frame (`_step1_frame`, `_step2_frame`). Every transition goes through `_swap_step2()` / `_refit()`, and each **returns False rather than failing silently** if the card isn't in the expected state, so callers fall back to the old rebuild path.
  - `_refit()` reads the card's **live** `winfo_x/y`, never a stale cached position — the card's anchor corner is recomputed and the see-through gap re-punched at the new corner on every resize.
- **`_step_header`** draws a numbered-circle badge (mockup style) + title + subtitle, with the action button (if any) reserving its width FIRST — **Tk labels do not clip**, they draw straight under a neighboring widget, so anything sized without accounting for the widest possible sibling silently loses text. This has bitten more than once; check it first before touching this row.
- **The compression never starts by itself.** After Fix All the card waits for an explicit **Compress with AI** or **Dismiss** — a 6-second job that freezes the UI for part of that is not something to start on the user's behalf, and stopping after grammar fixes is a normal thing to want.
- **Settings** (web, see above): tray left-click, or the card's own gear. Fixed size per page (`resizable(False,False)` + `pack_propagate(False)`), a scrolling viewport for pages that overflow (`General`, once it gained per-app category rows).

## 5. The model: audit, decision, and the compression-prompt fix

Full audit run 2026-07-21 against a 10-prompt eval set of realistic messy prompts, each with an explicit must-keep list (names, numbers, tools, formats, step order, hard constraints).

### 5.0 THE LAG: what it actually was (2026-07-21, measured)

Antonio reported the machine still going slow on Apply even after the model swap. It was real, and **the cause was not what four previous rounds of tuning assumed.**

Sampled during a real compress:

| | Idle | During compress |
|---|---|---|
| Free RAM | 3,661 MB | 2,534 MB, **no paging** |
| System CPU | 15% | **22%** |
| Cores busy | — | **2 of 22** |
| Worst stall of other threads | 1.6 ms | **12,058 ms** |

**22% CPU, no paging, 20 idle cores, and yet a 12-second freeze.** That combination rules out contention. Nothing was fighting for the machine; the work was being forced through two cores while the rest sat idle, inside one long native call that blocks every other thread in the process.

Every earlier fix (thread cap 4→2, BELOW_NORMAL priority, boosting UI/hook threads, paint-before-work) targeted contention, which is why none of them worked. **The 2-thread cap was itself the problem.** It was correct for Phi-3, where fewer threads reduced RAM thrash, and got carried over to a model that doesn't thrash.

Thread sweep, same prompt, same machine:

| Threads | Total | Frozen |
|---|---|---|
| 2 (shipped) | 14.1s | 11.92s |
| 4 | 7.2s | 5.96s |
| **8 (now)** | **5.3s** | **4.33s** |
| 12 | 4.9s | 3.85s |

Second finding from the same sweep: **our own system prompt is about half the cost.** At 2 threads, full prompt 14.1s vs a short one 7.0s. It's ~300 tokens of prefill paid on every single compress, and prefill is one dense chunk of work, which is exactly the shape of a single long freeze. Best measured combination was 8 threads + short prompt at 2.6s total and 1.33s frozen, but the long prompt is what fixes the compression quality (§5.2), so it stays until something is measured that beats it.

**Still open:** even at 8 threads there's a ~4s freeze, because the inference call blocks the whole process. The real architectural fix is running inference in a **separate process** rather than a thread, so the UI cannot be blocked by it at all. Bigger change, not attempted yet.

### 5.1 Memory, and why the model swap was still right

**Measured on the shipping build:** peak RSS **3.93 GB**, free RAM went 3.79 GB → 1.29 GB on load. Four rounds of CPU tuning barely helped because the bottleneck was never CPU.

The root cause is sharper than "the model is big". **Phi-3-mini has no grouped-query attention: 32 query heads and 32 KV heads.** Its KV cache is **384 KB per token, 1.61 GB at its 4k context**, on top of 2.54 GB of weights. That is the 3.93 GB.

| Model | KV cache/token | At 4k ctx | Weights (int4) |
|---|---|---|---|
| Phi-3-mini-4k | **384 KB** | **1.61 GB** | 2.54 GB |
| Qwen2.5-1.5B (GQA 12:2) | 28 KB | 0.12 GB | ~1.0 GB |
| Qwen2.5-0.5B (GQA 14:2) | 12 KB | 0.05 GB | ~0.83 GB |

Numbers read from the models' real `genai_config.json`, not estimated.

### 5.2 The bigger problem: it wasn't compressing prompts

**On 6 of 10 eval prompts the model did not compress the prompt, it executed it.** "Write me a product description under 80 words" came back as a product description. "I need to write an email to my landlord Mr. Patel" came back as `Dear Mr. Patel,`. The shipping-costs prompt came back as advice with **invented numbers**. Three outputs also hit the flat 200-token cap and were cut mid-sentence, and `_RAMBLE_SPLIT` then trimmed the wreckage into something that looked fine in the panel.

Must-keep retention was **76%**. Hard constraints ("under 80 words", "no exclamation marks", "since November 12th") were the things being dropped.

Cause: the shipping instruction was *"Rewrite this to be as short as possible while keeping the same meaning."* When the text you hand a model is itself an instruction, "rewrite this" reads as "do this". **This is a prompt bug, not a model-size bug**, and it was worth more than the model swap.

Fixed with three changes in `local_model.py`, all required, each one measured rather than assumed:

| Round | Change | Mean must-keep on the failing subset |
|---|---|---|
| 1 | Plain instruction (what shipped) | baseline, 6 of 10 prompts executed instead of compressed |
| 2 | Real compression system prompt | fixed 4 of 6 |
| 3 | + `<prompt>` fence, text declared data | **0.343**, and the survivors started failing *harder* |
| 4 | + one worked example | **0.553**, three of five survivors turned into good compressions |

**Instruction alone does not fix this; demonstration does.** Rounds 2 and 3 both told the model in plain language not to follow the text. Prompts phrased as direct commands ("write me a product description", "help me write a cover letter") kept getting executed anyway. A single worked example showing a "write me X" prompt being rewritten rather than obeyed moved it substantially. That is the usual result at this model size and worth remembering before writing another paragraph of instructions.

Watch out for the trap in round 3: fencing **improved** average compression (40.8% → 61.4%) and eliminated truncation, while **lowering** must-keep retention (0.766 → 0.655), because the cases that still failed now failed more aggressively. Compression percentage on its own is a misleading metric. Always read it next to retention.

Two failures survive all four rounds on Phi-3: `email_tone` and `hard_constraints`, both pure content-generation commands. This is a model capability limit, not a prompt problem, and it is the specific thing Qwen2.5-1.5B's stronger instruction following is expected to fix.

Also fixed: the flat 200-token cap is now `_token_budget()`, scaled to the input (floor 96, ceiling 1024, 1.15× input). A compression is by definition no longer than its input, so a flat cap was simultaneously too small for long prompts and too permissive for short ones.

### 5.3 Model decision: Qwen2.5-1.5B-Instruct int4

**Decided 2026-07-21.** `MODEL_SPECS` in `local_model.py` lists Qwen2.5-1.5B first and Phi-3 second; whichever is actually on disk wins, so the swap is a download (`tools_download_model.py qwen2.5-1.5b`), not a code change.

Why 1.5B and not 0.5B:

| | Qwen2.5-0.5B | Qwen2.5-1.5B | Phi-3-mini |
|---|---|---|---|
| IFEval strict-prompt | 27.9 | **42.5** | 42.3 * |
| Context | 32k | 32k | **4k** |
| Prebuilt CPU int4 on disk | 834–874 MB | 1.0–1.9 GB | 2.54 GB |

\* Phi-3's figure is from its own "Instructions Challenge" harness, same ballpark rather than strictly comparable.

**Qwen2.5-1.5B matches Phi-3 on instruction following at 40% of the parameters**, and instruction following is the entire job. The 0.5B was rejected because it saves only a few hundred MB (Qwen's 151,936-token embedding table is a fixed floor that doesn't shrink with the model) while giving up a third of that ability, in a task where the observed failure mode is already "ignored the instruction."

**No Fast/Default two-model mode.** It would trade ~300 MB for a third of the instruction following, it contradicts §1's locked "no confidence dial, same behavior for everyone", and a fast tier already exists: the rules stage runs instantly with no model at all.

**Swap completed 2026-07-21.** Qwen2.5-1.5B downloaded, verified, and running; Phi-3 deleted from disk, reclaiming 2.54 GB. Same 10-prompt eval, same shipped `rewrite_prompt()` path:

| | Phi-3 (as shipped) | Phi-3 (best prompt) | **Qwen2.5-1.5B** |
|---|---|---|---|
| Must-keep retention | 0.766 | 0.655 | **0.856** |
| Avg compression | 40.8% | 61.4% | 55.6% |
| Avg time per compress | 26.9 s | 40.2 s | **14.7 s** |
| Disk | 2.54 GB | 2.54 GB | **0.95 GB** |
| Prompts executed instead of compressed | 6 of 10 | 2 of 10 | **0 of 10** |

**Both prompts that survived all four rounds of prompt engineering on Phi-3 now pass.** `email_tone` went 0.17 → 0.83 and `hard_constraints` 0.20 → 0.80. That was the predicted outcome of the higher IFEval score and it held.

Remaining weakness, and it's a real one: **Qwen drops numbers on long, dense inputs.** `long_ramble` scored 0.40 (lost 400 orders, $39, $8, 70/30, Canada) and `debug_versions` 0.67 (lost the Python 3.12/3.9 versions). The shape of both compressions is right, the quantitative detail is not. `SYSTEM_PROMPT` lists numbers among the things to preserve but buries it in a list. Worth one targeted round, **measured, not assumed** — two of the four prompt rounds above made things worse, so do not change this prompt without re-running the eval.

### 5.3.1 Provenance, checked rather than assumed

**There is no official Qwen, Microsoft, or Intel ORT-GenAI CPU int4 build of Qwen2.5-1.5B.** Searched every relevant org directly:

- `onnx-community/*` (HF's own org) publishes Qwen2.5 ONNX, but **without `genai_config.json`**, so it's transformers.js format and ORT GenAI cannot load it.
- `amd/*` has proper ORT GenAI builds, but every 1.5B one is Ryzen AI NPU/hybrid. **This machine is an Intel Core Ultra 7 165H**, so they're unusable here. Their only plain-CPU build is the 0.5B.
- Everything else is community.

So `tools_download_model.py` points at `khanuckaeff/Qwen2.5-1.5B-Instruct-Olive-Onnx`, a community Olive build, and it was **verified against the official `Qwen/Qwen2.5-1.5B-Instruct` repo before downloading**:

| Check | Result |
|---|---|
| Vocab (151,643 entries) | Identical |
| Merge rules (151,387) | Identical, storage format only differs (newer `tokenizers` writes arrays instead of space-joined strings) |
| 22 special tokens | Identical |
| eos / pad ids | Match official `generation_config.json` |
| 10 architecture fields | Match official `config.json` |

The `tokenizer.json` **file hash differs** from official and that is a false alarm, see the merges row. Both community 1.5B repos produce the byte-identical tokenizer, which is what you'd expect from a deterministic conversion tool and not from tampering.

**What remains unverifiable:** the quantized ONNX weights themselves. There is no code-execution risk (ONNX graphs are data, unlike torch `.bin` pickles), but whether the quantization is any good only shows up when it runs. A bad quantization produces obviously incoherent text, so it fails loudly rather than silently.

Intel note for later: this machine has an **Intel AI Boost NPU**. Running inference there via OpenVINO would take the load off the CPU entirely, which is the original reason for the 2-thread cap and the UI lag. Different runtime stack, out of scope for now, but it's the most promising direction after this swap.

Mitigation already shipped: model auto-unloads after 180s idle (`MODEL_IDLE_UNLOAD_SECONDS`).

## 6. Hard-won findings (do not rediscover these)

**UIA / text access**
- **Use `control.GetPattern(PatternId.X)`, never the typed helpers** `GetValuePattern()`/`GetTextPattern()`. Those only exist on some control classes. A contenteditable chat box focuses as a `GroupControl`, which has neither, so they raise `AttributeError`, get swallowed, and you wrongly conclude "this app exposes no text." **This single mistake caused the dictation blindness, the clipboard workaround, the flashing, and the whole-transcript data-loss bug.**
- `ValuePattern.SetValue()` writes text directly. No clipboard, no Ctrl+A, no focus fight, no flash. Always prefer it.
- Claude's Electron build exposes no *writable* control (its only EditControl is the 261px find bar), so writing there needs the clipboard paste path.
- **The whole-page Ctrl+A guard needs ALL its checks, not `if/elif`.** It regressed on 2026-07-21 as `if expected_fragment: <tail check> elif len > MAX`, so passing a fragment **skipped the size cap entirely**, and a 9,347-character page grab was accepted as "the input box". The tail check cannot catch this alone, because **a whole-page selection always contains the user's own draft** (the composer is part of the page), so the tail is always found. Three independent guards now, all of them always applied: tail present, size proportional to what was actually typed (`max(1500, typed*6)`), and the absolute `CLIPBOARD_READ_MAX_CHARS` cap.
- **Don't run the clipboard read when the typed buffer is trusted.** It is the only operation that visibly select-all-flashes the box and the only one that can select the whole page. When nothing has been dictated or injected since the last reset, the buffer already holds exactly what was typed, so the read is pure downside. Gated on `_buffer_untrusted[0] or not get_typed_buffer()`.
- **Ctrl+A only selects the composer if the composer has focus.** Otherwise it selects the whole page. A read that captured a whole transcript once produced 31 junk suggestions and would have pasted the entire conversation into the input box. Guarded now: read must contain the last 12 typed chars, or be under `CLIPBOARD_READ_MAX_CHARS` (4000).

**Persisted window positions**
- **Re-validate any saved position against the CURRENT monitor layout on load.** The badge remembered `x=-1327`, which was a perfectly legitimate spot on a left-hand monitor at the time (virtual desktop started at `-4176`). Working on the laptop alone later, the desktop is `0..2256`, the badge restored itself off-screen, and the app looked completely dead while running fine. Antonio reported it as "where is it, it's not showing up now."
- `point_is_on_a_monitor()` uses `MonitorFromPoint` with `MONITOR_DEFAULTTONULL`; a NULL return means that coordinate is on no current display. `load_saved_badge_position()` checks the badge's **middle**, not its corner, and deletes the stale file so it self-heals instead of failing the same way on every launch.
- This applies to anything else positional that gets persisted. Laptop users dock, undock and plug into TVs constantly; the layout that existed when a position was saved is not the layout that will exist when it is restored.

**Win32 / ctypes**
- 64-bit handles need explicit `restype`/`argtypes`. Without them ctypes truncates to 32-bit and calls fail silently. Bit `SetPriorityClass`/`GetCurrentProcess` (ERROR_INVALID_HANDLE 6) and the `GlobalAlloc`/`SetClipboardData` family.
- **`WS_EX_NOACTIVATE` must be applied *after* the window is realized.** Before realization `GetParent(winfo_id())` returns 0 and `SetWindowLongPtrW(0, ...)` silently fails, leaving the popup activatable, which steals focus from the target box and breaks Apply. Build the window hidden, `update_idletasks()`, apply style, then show.
- `SetProcessDpiAwareness(2)` must run before any window is created, or windows land off-screen on scaled displays.
- Low-level hooks (`WH_KEYBOARD_LL`/`WH_MOUSE_LL`) need `hMod=NULL`, not `GetModuleHandle`.
- `LLKHF_INJECTED` filtering stops self-triggering, but also means **dictation is invisible** to the keystroke buffer.
- `AttachThreadInput` is required for reliable `SetForegroundWindow` after long delays (plain calls only work inside the "recent input" grace window, which a 15-30s AI run blows past).

**Click vs drag, and silent failures**
- **A click-vs-drag threshold of 3px, summed across both axes, is not a click threshold, it is a "never clicks" threshold.** 2px of horizontal drift plus 2px of vertical failed it. Windows' own `SM_CXDRAG`/`SM_CYDRAG` is 4px **per axis** and assumes a mouse; a trackpad click on a scaled display routinely moves further. Result: every badge click was recorded as a reposition and the review card never opened. Use `BADGE_CLICK_SLOP_PX` (system metric, floored at 8) and compare per axis, never summed.
- **The log recorded drags but never clicks**, which made "clicking does nothing" indistinguishable from "the click wasn't detected". Diagnosing it needed the *absence* of `open_suggestions` after a `badge manually repositioned` line, which is a terrible signal to have to reason from. Both branches log now, including the case where `on_click` is None because the text is under `MIN_TEXT_LENGTH_TO_ANALYZE`. **If a user-facing action can do nothing, log the nothing.**
- Color-keyed (`-transparentcolor`) pixels are genuinely **click-through**. The shaped badge is 84% clickable versus 100% for the old full square tile. Fine in practice, but it means the visible artwork *is* the hit target, so any future shape change is also a hit-target change.
- **The badge is always clickable**, even with no suggestions and even below `MIN_TEXT_LENGTH_TO_ANALYZE`. It used to be inert on short text, which just reads as broken. The card handles it: Step 1 says "No grammar or spelling issues found" and Step 2 still offers "✦ Optimize Now". Grammarly's icon always opens something; so does this one.

**Colour-key transparency (`-transparentcolor`)**
- **It removes only pixels matching the key EXACTLY, so soft alpha and colour-keying are fundamentally incompatible.** Downscaling the mark with LANCZOS leaves a rim of semi-transparent pixels plus a little resampling ringing. Tk composites those against the dark label background, landing them a shade or two off the key, and Windows keeps them: a scatter of dark speckles tracing the old square bounds. Antonio reported it as "the edges of the square are still visible, it looks bad."
- Fix is `_flatten_for_colorkey()`: **binary alpha**. Above `_BADGE_ALPHA_CUTOFF` the pixel becomes solid artwork, below it becomes exactly the key colour. Slightly crisper edge, zero halo. Any surviving pixel that happens to equal the key gets nudged, or Windows would punch a hole through the artwork.
- **Simulating the colour-key in PIL will not reproduce this bug.** Earlier checks did exactly that and looked perfect while the live badge was speckled. Drive the real Tk widget and screenshot it (`scratchpad/inspect_badge.py` pattern): create the badge over a white Toplevel, `ImageGrab` the region, magnify.

**Tkinter**
- **Tk's clipboard uses delayed rendering.** It claims ownership and only supplies text when asked, which needs Tk's event loop running. `apply_new_text` sleeps between keystrokes, so the paste came back empty and only the Ctrl+A highlight landed. **Use Win32 `SetClipboardData` instead.**
- `update_idletasks()` does layout but **not** repaint. Use `update()` to force a full paint before starting CPU-heavy work, or the loading card renders half-blank.
- Poll-driven repositioning fights an in-progress drag. Guard on `_drag_start is not None`, otherwise the badge snaps back and saves the wrong coordinates.
- Position popups from the badge's **live** location at display time, not coordinates captured earlier (they go stale the moment the badge is dragged).
- `-transparentcolor` colour-keys a colour to true transparency (Windows only).

**PyInstaller**
- **`comtypes.client` breaks when frozen.** It pulls in codegen (`comtypes.client._generate`, `comtypes.tools.codegenerator.*`) that PyInstaller doesn't bundle, so spell-check was silently dead in the packaged build while working perfectly from source. Use `comtypes.CoCreateInstance` directly + `hiddenimports`.
- Pure-Python modules go **inside the archive**, not as loose `_MEIPASS` files, so checking for files there proves nothing.
- Set `icon=` in the spec's `EXE()`, and `SetupIconFile` in the .iss, they're separate.

**Spelling**
- **A misplaced space is not a spelling error, and asking a spell checker to treat it as one produces confident nonsense.** Antonio hit this: `"tak eto"` came back as `"take ego"`. Windows sees two independent words and fixes each in isolation, `tak`→`take` and `eto`→`ego`. Neither correction can see the other, and the real error is in neither word. The fix is to ask a different question: glue the pair back together and find the split where **both** halves are real words. `taketo` → `take|to`.
- **Tie-break toward moving the space RIGHT.** `"tak eto"` is genuinely ambiguous, `ta|keto` scores identically to `take|to` and "keto" is in modern dictionaries. The dominant real typo is releasing space one keystroke early, so rightward wins. Both of Antonio's examples are exactly that.
- **`finditer` on a `"word word"` regex cannot enumerate adjacent pairs.** Matches are non-overlapping, so in `"to lik ethis"` it consumes `"to lik"` and never looks at `"lik ethis"`. The rule worked on the bare phrase and silently did nothing inside a real sentence. Walk the token list with `zip(tokens, tokens[1:])` instead.
- The rule only fires when at least one of the two words is already misspelled, and only searches ±3 characters, so correctly-typed text is never re-split.
- **Deliberately NOT implemented: splitting a single merged word** (`"tothe"` → `"to the"`). Tempting, and it is the sibling of the above, but measured against real words a spell checker flags: `github` → "git hub", `dropbox` → "drop box", `javascript` → "java script". All three flag as misspelled and all three split into two valid words. For a tool whose users write technical prompts that is unacceptable. `alot`, `infact` and `everytime` would have been nice wins; they are not worth mangling every product name.
- Cost check: `analyze()` is 97 ms worst case on a 165-word prompt full of typos, against a 700 ms poll budget. `winspell.is_correct()` is cached because otherwise every 0.7 s tick would be hundreds of COM round-trips.

**Screen size and DPI**
- Every dimension was in **physical pixels** with the process per-monitor DPI aware, so nothing scaled. The card was 560px on Antonio's 144 DPI laptop (~3.9 inches) and would be the same 560px on a 96 DPI 1080p screen (~5.8 inches), appearing about **50% larger**. He asked for the size he has now to be the universal one.
- **`UI_SCALE = 1.0`, a hardcoded constant. The UI is ONE FIXED SIZE on every screen: card 560px, badge 58px, base text 15px. Do not make this DPI-dependent again.**
- Four attempts were made to be clever about this, and all four failed. Recorded so nobody repeats them:
  1. `dpi / 144` (constant **physical** size). Monitor landed at 0.67, too small.
  2. `max(1.0, ...)` (design size as a **floor**). Both screens identical, monitor then too large.
  3. A curve **anchored through two measured screens** (96 -> 0.80, 144 -> 1.00). Looked principled, and the anchors were even tuned by eye on the real hardware.
  4. Retuning that curve's monitor end twice more (0.80 -> 0.72 -> 0.61).
- **Why they all failed is the same reason each time, and it isn't about picking better numbers.** Any DPI-dependent size means the UI silently changes underneath the user depending on which monitor a text field happens to be on. One wrong monitor reading, and it resizes on a screen the user explicitly said not to touch. That is what happened, repeatedly, and no amount of anchor tuning fixes it: the *mechanism* was the bug.
- Antonio's call, and it is the right one: **"don't make it change sizes, just keep the previous laptop size and that's it for all."** Predictable everywhere beats optimal anywhere, especially for a floating widget the user did not ask to think about.
- `S()` and `FONT_SCALE` are kept because they make the whole UI adjustable from one number if it is ever needed. `S(px)` is currently an identity function.
- `S(px)` is applied to every design-pixel literal in the two UI classes.
- **`SetProcessDpiAwareness` MUST run before `_monitor_dpi()`**, and it now sits directly above it at the top of the module. `GetDpiForMonitor` reports **96 to a DPI-unaware process** regardless of the real monitor, so with the call ~400 lines further down, `UI_SCALE` was computed while still unaware. Worse than wrong, it was **non-deterministic**: the same binary logged `UI scale 1.00 (monitor 144 dpi)` on one launch and `0.67 (monitor 96 dpi)` on the next.
- The startup log line `UI scale X (monitor N dpi, ...)` exists precisely because of this. Check it first for any "the UI is the wrong size" report; it distinguishes a bad scale calculation from the display genuinely having changed.
- `tk scaling` is pinned to `(96/72) * UI_SCALE * FONT_SCALE`. Fonts are specified in POINTS, so without pinning it, type and layout would drift apart on other machines.
- **`FONT_SCALE = 1.28`, and it is not arbitrary.** Tk's native conversion follows the Windows shell convention where 9pt Segoe UI is standard and lands at **12px**. That is correct for a native app and wrong for this one, because the card floats on top of Claude and ChatGPT, whose web UIs set body text around **16px**. Side by side, ours looked shrunken. Antonio: "look at the Claude text and see ours, notice how ours is smaller, make it relative size." Base text now renders at 15px. **The reference for this app's type is the app underneath it, not the Windows shell.**
- Clamped to `[0.62, 1.75]` so a strange DPI reading can't produce an unreadable card or one that eats the screen.
- **Absolute reserves must scale too.** `wraplength=POPUP_WIDTH - 260` is fine at 560 wide and leaves 113px at 373 wide. Anything of the form `POPUP_WIDTH - N` needs `S(N)`.
- Verified by rendering all four card states at 96, 144 and 192 DPI (`scratchpad/render_at_scale.py` patches `UI_SCALE` at import time, before the constants are computed). Do this after any layout change; the failure mode is clipping, and clipping is invisible in code.

**Icons**
- A transparent logo is **invisible on light backgrounds** at taskbar sizes, and white monogram detail disappears entirely. App icons need a dark tile baked in. Verify by rendering at 16/24/32/48px over both light and dark.
- **That tile belongs only where Windows draws us as an application** (taskbar, tray, Explorer, settings window, installer). Putting it on the floating badge produced a visible black box that made the indicator read as a little app window parked on the user's text field. Antonio rejected it on sight. The badge instead fills the mark's **own teardrop silhouette** (`tools_make_badge_asset.py` → `assets/badge.png`): same legibility, no box.
- The badge window colour-keys `BRAND_DARK` (`#0b0b0d`) to true transparency, so **anything filled with exactly that colour disappears**. The first version of the filled badge was invisible for this reason. The fill is `#0e0e11`, visually identical, not the keyed value. Caught by rendering it before shipping, not by reading the code.
- **An exe with no version resource is named by its file name** everywhere Windows names a running app: Task Manager, taskbar tooltip, file properties. Every on-screen string said Comprsly while Windows still said TokenSaver. Fixed with `version_info.txt` (`version=` in the spec's `EXE()`) plus `SetCurrentProcessExplicitAppUserModelID`.
- **The shell caches exe icons by path.** Rebuilding with a new `.ico` at the same path can keep showing the old icon indefinitely. Renaming the exe gives a fresh cache key and is the reliable fix; `ie4uinit.exe -show` is the softer one.

**Testing discipline**
- Modern Notepad opens new *tabs* in an existing window. Targeting by `ClassName='Notepad'` attaches to whatever the user already had open. **This destroyed one of Antonio's unsaved documents.** Always target the exact spawned handle, or a throwaway file.
- Render UI offscreen and **screenshot it** before shipping. This caught a completely missing Step 2 button and a clipped title that code review would not have.
- The `debug.log` is the primary tool. "It ran without raising" is not evidence it worked.

## 7. Deliberate exceptions worth knowing

- **Install folder renamed `Token Saver` → `Comprsly` (2026-07-22), reversing the old grandfather exception.** Antonio asked for it directly. `installer.iss` keeps `MyAppName` (display) and `MyAppFolder` (path) separate, and `MyAppFolder` is now `Comprsly`. Migration is belt-and-suspenders: the installer copies settings/history/badge_position out of any old `Token Saver` folder and deletes it (`MigrateLegacyData`/`RemoveLegacyFolder` in installer.iss), and `main.py._migrate_legacy_data_dir` copies the small data files app-side too. `UsePreviousAppDir=no` is REQUIRED, else a same-AppId re-run defaults back to the old folder and silently defeats the rename. A stale autostart path is self-healed (`main.py.heal_launch_on_login` + installer `FixAutostartRegistry`).
- **`MUTEX_NAME` stays `TokenSaverSingleInstanceMutex`.** Nobody ever sees it, and changing it during the rename would have let an old build and a new build run at the same time.
- **No real POS-tagging grammar.** Genuine grammar checking needs a heavy NLP tool or another ML model, both of which would reintroduce the memory problem. Only unambiguous rules are implemented; anything deeper rides on the AI pass. **Comma PLACEMENT is deliberately not attempted** (2026-07-22): rule-based comma insertion needs POS understanding and false-fires constantly on technical prompts. Comma SPACING is handled (space-before-punct + missing-space-after); placement rides on the AI pass.
- **True inline underlining inside another app's text is impossible** for a native desktop app (no DOM access). The itemized panel list is the realistic equivalent. The Chrome extension *can* do real underlines.

## 10c. Grammar coverage — the go-to-market level-up (2026-07-22, v0.9.7)

Antonio's question after the fixes: "is there another LEVEL, specifically in grammar/writing/punctuation?" Ran a diagnostic across the error categories a Grammarly-class tool is judged on. Found the engine caught **zero** of: homophones (your/you're, to/too, then/than), `should of`-family, and subject-verb slips — and worse, the plain contraction rule turned "he dont" into "he don't" (agreement still wrong). This is the biggest visible quality gap for market.

Added `_find_confusable_suggestions` (new §"Confusable words / agreement"), tiered strictly by how safely a plain rule can disambiguate, and **measured against a 31-case false-positive corpus of legit prompts before shipping** (0 FP, the bar). Every pattern is gated to a construction where the error reading dominates; anything needing real parsing is left to the AI pass (same line §7 draws).

Shipped patterns (recall / FP measured):
- **modal + "of" → "have"** (`should/would/could/must/might/may of`), excluding the "of course"/"of all" idioms. Near-zero-FP by nature; the standout win.
- **3rd-person-sing + "dont" → "doesn't", + "have" → "has"** (he/she/it/this/that). Also fixes the "he don't" interaction bug — confusables claim the span before the contraction rule.
- **"to" → "too"** before a degree word (much/many/late/hard/…), gated to a preceding LINKING verb ("this **is** to hard", "there **are** to many") and skipping partitives ("to many **of** them"). The linking-verb gate is what killed the prepositional FPs ("sent it to many teams", "switch to hard mode").
- **"then" → "than"** ONLY when immediately preceded by a comparative (better/more/rather/…). Adjacency-only on purpose: an earlier clause-scan + generic "-er ending" test fired on nouns ("header **then** the footer") and distant "rather…then merge". Costs the non-adjacent "more work then i thought" (accepted; AI pass covers it).
- **"your" → "you're"** only for "your welcome"/"your gonna"/"your about to" and "your <gerund> to" ("your going to"). General your→you're is NOT attempted (real possessives: "your right hand", "your going rate").

Deliberately NOT done (needs real context / Antonio's decision): general homophones (their/there, its/it's stays excluded per §7), the LLM-in-the-loop validation layer the 2nd audit proposed (trades the instant-rules design for seconds of latency; the cheap 80% — frequency tie-break + these gated rules — shipped instead).

## 10h. Compress speed: prefill caching + prewarm (2026-07-22, v0.9.13)

Antonio: compress "sometimes just really slow." Measured from debug.log (model-load lines + timestamp gaps) + a direct timing run rather than theorizing:
- Warm compress ~9.8s, of which **~9s is PREFILL of the ~700-token SYSTEM_PROMPT** (generation of the actual output is <1s at ~26 tok/s). The system prompt is byte-identical every call yet was re-prefilled every time.
- Example 4 (added §10b) cost ~2s/compress on its own (703 vs 566 prompt tokens) — noted, but caching made trimming unnecessary.
- Cold reload after the 300s idle-unload = a full model load + first inference (~25s), the worst "really slow" moments.

**Fix: KV-cache the system-prompt prefill via `og.Generator.rewind_to` (onnxruntime-genai 0.14.1).** New `rewrite_prompt_cached` (worker-side): prefill the fixed system block ONCE per model load, then per compress append only the user block, generate, and `rewind_to` the cached checkpoint (keeps the system prefix warm). `_split_template` splits the chat template at the user-turn special token so the two halves tokenize independently (why the cached prefix stays valid). The worker (`run_inference_worker`) now calls it; **any exception resets the cache and falls back to the fresh `rewrite_prompt`**, so correctness never depends on the cache. Cache reset on model unload/force-unload (generator holds a model ref); rebuilt lazily (model-identity + spec-key checked).

Measured, verified BEFORE shipping (both source and the FROZEN worker exe):
- **6-8x faster warm**: ~0.8-1.1s vs ~6.9s. First compress per load still pays a one-time ~6s cache build (folded into cold start).
- **BYTE-IDENTICAL output** to the fresh path across varied prompts (0 mismatches) — greedy/do_sample=False, so retention is mathematically unchanged.
- Full 13-prompt eval through the cached path: **mean retention 0.861, identical to baseline**; per-compress 0.6-2.8s after the cold first.
- Frozen `Comprsly.exe --inference-worker` over its real stdin/stdout: 10.8s cold, then 0.98s / 0.88s warm; log shows "prefill cache built" then cached rewrites.

**Cold-start hidden via background prewarm (v0.9.13).** The one remaining slow moment was the first compress after launch/idle (~10s: worker spawn + model load + one-time cache build). `prewarm_via_subprocess()` fires that in the BACKGROUND the moment the review card opens in an LLM app (`open_suggestions`, gated on is_llm + ai_enabled + model downloaded + worker not already warm), so the load overlaps the seconds the user spends reading their grammar fixes. Worker gained a `{"warm": true}` command (loads model + builds cache via a trivial discarded compress). Holds `_worker_lock` while warming so a Compress landing mid-warm waits for it rather than spawning a second worker. Verified: prewarm during a ~10s read window → first real compress **0.70s** (source) / **0.58s after an 8.74s background warm** (frozen exe). Net: badge click warms it, Compress feels instant.

Also: **`MODEL_IDLE_UNLOAD_SECONDS` 300 -> 900 (15 min)** so the warm model + KV-cache survive normal work-session gaps instead of paying cold reload every few minutes (Antonio's RAM-vs-speed call; 15 min is the balanced default, easily changed). Still open / not chosen: trimming the prompt / dropping Example 4 (caching made it moot), streaming (won't help — generation is already <1s; the wait was prefill, now cached).

## 10i. Compression content-loss on rambling-context-then-question prompts (2026-07-24, v0.9.45)

Antonio hit it directly (not an audit): a practice prompt with real situational context (a meeting, reasons, a busy week, a notification overload) ending in a question compressed to **just the closing question**, discarding everything before it. Reproduced exactly against the shipping model: 82 words → 12 words, "Weigh pros and cons and recommend based on schedule and long-term goals." **First attempt (Example 5, a worked demonstration, same pattern as Examples 1-4): did NOT clear the bar.** Nudged the target case (0.50→0.67, still over-compressed and still missing content) but REGRESSED a previously-solid case (`product_desc` 0.83→0.67, newly dropped "80 words"), mean retention flat, low-retention count up (2→3). Per this project's own rule (two of four past prompt rounds made retention worse while looking better on one metric), reverted rather than shipped. Confirmed clean revert (Example 5 absent, product_desc back to 0.83 standalone).

**Real fix: a runtime collapse guard, not another prompt bet.** `_looks_collapsed(source, out)` flags the same signature the eval already calls "over-compressed" (>70% word cut) on a source long enough that it's genuinely suspicious (>=40 words, so short prompts can still legitimately compress hard). On a hit, retries ONCE with `_RETRY_REMINDER` appended to the system prompt (explicit "don't drop the context, keep every fact" instruction). If the retry is still collapsed, returns an ERROR instead of a gutted result — `compress_with_ai` in main.py already has an existing, accepted fail path for this (dismiss cleanly, keep the rules-cleaned Step 1 text, no wipe, no dead end), so this needed zero new UI code, it just fails toward a path that already existed. Wired into BOTH `rewrite_prompt` (the fresh/eval path) and `rewrite_prompt_cached` (the actual live worker path the shipped app uses) — the retry always goes through the fresh path even from the cached caller, matching the existing "any problem resets the cache and falls back fresh" philosophy.

Measured before shipping: full 14-prompt eval with the guard active — `context_then_question` now correctly ERRORS (fails safe) instead of returning the gutted 12-word result; **every other case in the suite is byte-identical to the pre-Example-5 baseline, zero regressions**; mean retention (over the 13 non-errored cases) 0.861, over-compressed 0/13, low-retention 1/13 (`meeting_notes`, a separate pre-existing issue, unaffected). Directly verified through `rewrite_prompt_cached` (the real worker code path, not just the eval's `rewrite_prompt`) with Antonio's exact original wording: correctly returns `(None, "compression dropped too much content")`; a normal case through the same cached path still compresses correctly, unaffected. Deployed 0.9.45.

### v0.9.46 correction: never hard-fail, always return best-effort (same day)

Antonio, direct: "id rather have a compresed output than a failed one" — a hard failure (no AI result at all) is a worse tradeoff than an imperfect-but-real compression, and he wants the app to never hand back nothing. Two changes:

1. **`_RETRY_REMINDER` was a plain-text instruction and did NOTHING** — verified directly: `rewrite_prompt` with the reminder appended returned the exact same 12-word collapsed output, byte-for-byte, as no reminder at all. Same finding this file has hit repeatedly ("demonstration beats instruction" at this model size). Replaced it with the ACTUAL Example 5 worked demonstration (design-subscription-renewal domain) that was reverted from the main `SYSTEM_PROMPT` in the first attempt above — but now used **only inside the retry**, which the collapse guard already restricts to inputs that already failed once. It can never fire on a healthy compress like `product_desc`, so it can't regress it — this is the exact fix that was missing when Example 5 lived in the main prompt used by every compress.
2. **On a still-collapsed retry, return the best available candidate instead of an error.** Whichever of the original or retried attempt kept MORE words (the practical signal of "dropped less") is returned as a success. A true generation error (empty output) still falls through to the caller's existing "AI failed, keep rules-cleaned text" path — that part is unchanged, this only changes what happens when generation *succeeds* but still looks collapsed.

Measured again, full 14-prompt eval: `context_then_question` **0.50 → 0.67 retention, and now ALWAYS returns a result** (output now explicitly keeps "attending the meeting," previously vanished entirely); **every other case (including `product_desc`) is byte-identical to the original pre-Example-5 baseline, zero regressions**; mean retention 0.847 over all 14 (no more excluded error rows). Deployed 0.9.46.

### Review card: web UI attempted, technically succeeded, rejected anyway (v0.9.14–v0.9.34)

### Grammar engine: aligned to a tiered-confidence spec (v0.9.42, source: `grammar-engine-master-prompt-v2.md`)

`suggestion_engine.py` already had most of the spec's substance (transposition-weighted edit distance, keyboard-adjacency ranking, protected spans, single-pass highest-offset-first apply). Three things were added to close the gap:

1. **`_SPELLING_OVERRIDES`** — a curated misspelling→correction table (spec's Step 2), checked before the OS spellchecker's own candidate ranking, because generic edit distance frequently resolves a real typo to the wrong real word.
2. **Confidence tiers** via `_tag(suggestions, tier, reason)`, applied per-finder in `analyze()`. Tier 1 = auto-safe, Tier 2 = single objectively-correct fix (apostrophes, a/an), Tier 3 = genuine judgment call (homophones/confusables, filler/verbose/redundant style trims). The review card's checkboxes default checked for Tier 1/2 and **unchecked for Tier 3**, so a bulk "Apply all fixes" only ever applies what's genuinely safe — this is the same principle as the long-standing "never auto-fix its/lets/then" rule, now generalized into an explicit, per-suggestion property instead of a handful of special-cased exclusions.
   - **Comma-after-intro and terminal punctuation were tiered, then re-tiered.** Originally Tier 3 (reasoning: casual chat text often omits end punctuation and intro commas on purpose, forcing them would impose a style preference). Antonio's explicit call, later the same day: auto-check them anyway (Tier 1 now). `reason` text is stored on every suggestion regardless of tier but is **not currently rendered anywhere in the card UI** — confirmed by grep before making this change, so re-tiering had zero UI side effects beyond the checkbox default.
   - **Confusable coverage is incomplete by design** (precision over recall, per the project's standing philosophy) but real gaps get closed when found in testing: `except`→`accept` (modal/infinitive position gate, e.g. "should except" — mirrors the existing `_MODAL_OF_RE` pattern) and `were`→`where` (gated on a small set of location/continuance verbs immediately before it — `know`/`ask`/`tell`/`stay`/`live`/etc.) were added this way, each verified against 5+ false-positive probes (legitimate "except the crust", legitimate past-tense "were") before shipping.
3. **Round-trip verification** in `apply_suggestions`: after assembling the edited text, it's rebuilt a second way (splice the same kept edits onto the untouched original) and compared; any mismatch outside the intended spans fails safe and returns the ORIGINAL text rather than risk returning corrupted content. See §10i for the separate, larger compression-specific safety net (`_looks_collapsed`), which is a different mechanism for a different failure mode (the AI dropping real content, not the rules engine misapplying a span).

### Grammar: dropped-space-before-"I" merge (v0.9.49, 2026-07-24)

Antonio: typing "afteri" (meaning "after I") was being spell-corrected to plain **"after"** — the pronoun silently disappeared instead of the space being restored. Cause: the flagged non-word fell straight to the generic typo-distance ranking, which found "after" (drop the trailing "i") a closer edit than recognizing the merge. There was no dedicated rule for "real word glued to a dropped-space capital I" — `_find_orphan_letter_join_suggestions` and `_find_misplaced_space_suggestions` both require an *existing* space to work with; "afteri" has none.

Fix: `_dropped_space_before_i(word)` in `suggestion_engine.py`, checked inside `_find_spelling_suggestions` before falling back to the generic candidate ranking. Deliberately narrow (precision over recall, same house style as every other confusable/merge rule): only fires when the word minus its trailing "i" is in a small closed set of connector words that are naturally followed by the pronoun "I" in real sentences (`_I_MERGE_PRECEDERS` — after/before/until/since/when/if/because/and/but/etc.). This is what keeps it from ever touching a genuine word ending in "i" — but in practice it doesn't even need to, since real i-ending words ("taxi", "ski", "alibi", "hi", "sushi") already pass the dictionary check and never reach a spelling suggestion at all; the gate only matters against OTHER flagged non-words that happen to share a connector-word prefix (verified clean on "toi"/"hii", which fall through to the pre-existing generic correction, unchanged, since their prefixes aren't in the set). Lands as Tier 1 (auto-checked), same as the rest of `_find_spelling_suggestions`'s output. Deployed 0.9.49.

## 10k. Grammar batch: its/it's, your/you're reverse, principal/led/fewer, "I doesn't" agreement bug, override-table reachability (2026-07-24, v0.9.50)

Antonio ran an isolated grammar-only diff against 6 test prompts (AI off, Fix All only) and reported a long, specific critique list. Every item was reproduced against the actual engine before touching anything, matching the project's standing verify-first rule.

**Root cause found and fixed — `_SPELLING_OVERRIDES` was never actually reachable for words winspell itself considers correct.** "wat" (meant "what") stayed untouched no matter what was in the override table, because the table was only ever consulted for words winspell's own `check()` had ALREADY flagged as wrong — and winspell apparently accepts "wat" as a real word (a name/dialect form), so it never appears in that flagged list at all. Fixed by scanning every word token against the override table **independently of winspell's own opinion**, ahead of and regardless of the flagged-word loop (claimed spans are protected so the flagged-word loop can't double-suggest). This is what the spec's own "check the override table BEFORE any distance-based guessing" actually requires; it was previously downstream of the OS's flagging decision. Added `"wat": "what"` to the table now that it's reachable.

**Real compounding bug — "I dosent" was being auto-fixed to "I doesn't", a NEW grammar error, by Fix All.** `_SV_DONT_RE` (he/she/it/this/that + dont/doesnt → doesn't) only ever recognized the correctly-spelled inputs, not the misspellings "dosent"/"doesent" — so those fell through to the plain `_CONTRACTIONS` dict, which blindly maps them to "doesn't" regardless of subject. Fixed in two parts: (1) extended `_SV_DONT_RE`'s input set to also recognize "dosent"/"doesent"; (2) added the missing REVERSE direction, `_SV_DOESNT_TO_DONT_RE` (I/you/we/they + any doesn't-family spelling → "don't"), which claims the span first (confusables run before contractions) so the subject-mismatched auto-fix can never fire again.

**Tier fix, direct side effect of the above.** Extending `_SV_DONT_RE` moved "he dosent"→"doesn't" from the plain contraction rule (Tier 2, auto-applied) into `_find_confusable_suggestions`, which is blanket-tagged Tier 3 in `analyze()` — that would have silently DOWNGRADED an objectively-correct fix to "needs manual review," a real regression the fix itself would have introduced. The spec explicitly tiers subject-verb agreement and "should of→have" as Tier 2, not 3, so `add()` inside `_find_confusable_suggestions` now accepts an optional `tier=` override (used for modal-of, both dont/doesnt agreement rules, and have/has), and `_tag()` was changed from unconditional overwrite to `setdefault` so an already-stamped tier survives the finder's blanket call. Net effect: "should of"/"he dont"/"he dosent"/"I dosent" all now correctly auto-apply via Fix All (Tier 2); genuine homophones in the same function (to/too, then/than, your/you're, its/it's, principal/principle, led/lead, less/fewer) stay Tier 3/unchecked as intended.

**New confusable coverage, all in `suggestion_engine.py`, same narrow-gated-construction house style as every existing rule, each checked against a false-positive probe before shipping:**
- **its → it's** (previously fully excluded — "needs context"). Three specific constructions ARE unambiguous regardless of context: `its been` (a participle never follows a possessive determiner), `its a/an/the` (two determiners in a row can't parse), and `its` + a curated closed set of predicate adjectives/adverbs (`_ITS_PREDICATE_WORDS` — unfair, ready, obvious, probably, definitely, etc. — none of these are nouns, so "its X" can't be a possessive). General its/it's (e.g. "its color") is still deliberately excluded. Verified clean against "its color", "its recurring theme", "its opening was delayed" (all legitimate possessives, untouched).
- **you're → your** (the REVERSE direction — only your→you're existed before). Gated to `you're NOUN is/are/was/were` with a curated concrete-noun list (`_YOURE_TO_YOUR_NOUNS`), not a generic any-word gate — the trailing be-verb is what makes it safe ("you're bag is heavy" can't parse as "you are bag is heavy," so "bag" must be a possessed noun). A generic gate would have misfired on "you're smart is what everyone says" (adjective completing one clause, "is" starting a new one) — verified this exact case stays untouched.
- **principle → principal**, gated to `principle of the/a/an <institution-noun>` (school, university, company, etc.) — specific enough that the rule/belief reading essentially never occurs there. "principle of least effort"/"principle of relativity" verified untouched.
- **led → lead**, gated to a curated role-noun list (`_LEAD_ROLE_NOUNS` — singer, guitarist, actor, etc.), the fixed "lead singer" phrase pattern, not the classic past-tense-verb error. "I led the team to victory" verified untouched.
- **less → fewer**, gated to a curated countable-plural-noun list (`_FEWER_NOUNS`) rather than a generic plural detector, since English mass-noun exceptions ("less news", "less stress") are common. Both verified untouched.

**Known residual gap, honestly documented rather than chased further:** a word that's BOTH a candidate for one of the new its/it's predicate-word rules AND separately misspelled in the same span (e.g. "its probly" — "probly" itself needs fixing to "probably" before the its-rule's exact-word match can recognize it) doesn't get caught in one pass; the two rules don't chain. Narrow, rare, not attempted this round.

All of the above verified via targeted true-positive and false-positive test batteries (not just the reported cases) before shipping. Deployed 0.9.50.

## 10l. Download progress inconsistency, statement-inversion compression bug, theme control cleanup (2026-07-25, v0.9.51)

**Download progress bug: two real, verified causes, both fixed.**
1. **No live polling existed at all.** `settings.html`'s `refreshModel()` was only ever called once on page load and once 600ms after clicking Download — there was no repeating refresh while a download was actually in progress. What looked like "0%→22%→0%→done" was largely just disconnected snapshots from whichever moment the page happened to be viewed, not a genuinely broken value. Fixed with `_ensureModelPoll()`: a `setInterval` that polls every second WHILE `m.downloading` is true and stops the instant it isn't.
2. **A transient failure on any ONE of the ~13 model files wiped the ENTIRE download back to 0%.** `download_model()`'s per-file `urlopen`/stream had no retry — one HuggingFace CDN blip (entirely normal over a multi-minute, ~1GB transfer) fell straight to the outer `except`, which deletes the whole `.partial` directory and reports failure, discarding every other file's progress too. Added `statement_not_request` to `tools_eval_compression.py` (retention 0.83 by word-match, but the real defect — the inversion — isn't something word-retention alone can score, hence the `meaning_note` for manual review). Attempted the standard fix (a 6th worked example, different domain — a venue/rooftop closure — teaching "a statement stays a statement"): it DID fix the target's framing (output became "Update: ..." rather than a question) but dropped MORE actual content in the process (retention on that same case fell further, 0.83→0.33) and REGRESSED two previously-fine cases (`travel_plan` started answering instead of compressing; `role_call_order` dropped real content). This is a different failure class from the over-compression the runtime guard (§10i) catches — it's a meaning/framing inversion, not a length problem, so a word-count-based runtime check can't detect it, and (see §10m) a second, more targeted retry-only worked example ALSO failed to fix it. The eventual fix (§10m) is a deterministic mechanical rewrite, not another prompt bet.

**Theme control cleanup + new card toggle.** Antonio: the Settings header's theme toggle duplicated the General tab's own Theme control one page away — removed the header one (`webui/settings.html`'s `.tbar`), General is now the only place in Settings to change it (`applyTheme()`'s shared `querySelectorAll` still works fine with the header element gone). ## 10m. Statement-inversion fix, review-card perf investigation, punctuation/grammar fixes, LLM-only scope reversal (2026-07-25, v0.9.52)

### Statement-to-request inversion: fixed (closes the §10l open item)
The retry-only-worked-example pattern that fixed the collapse bug (§10i) was tried here first, on the theory that it's the same "confine the fix to a retry path so it can never regress a healthy compress" shape. Built `_looks_like_fabricated_status_request()` (narrow curated-phrase detector: output opens with "update me on X"/"let me know the status of X"/etc. AND the source's own opening never asked for that) and a retry-only worked example. Measured directly: even a SECOND example, restructured to mirror the real case's discourse shape almost exactly (statement+reason → binary choice → deadline → reason for the deadline, not just a different vocabulary domain), still reproduced the same fabricated opener on the real case, and additionally dropped MORE content than the original. Regeneration just isn't reliable for this specific failure at this model size — a second real, verified instance of "demonstration doesn't always transfer," beyond what §10i/§10j already found.

**Real fix: a deterministic mechanical rewrite, not another regeneration.** Since the detector is a narrow, high-precision curated-phrase match (same house style as every confusable rule in `suggestion_engine.py`), `_defabricate_status_request()` surgically rewrites just the fabricated opener sentence — "Update me on the vendor's shipping status." becomes "The vendor's shipping status:" — keeping 100% of the model's real content (including the object noun phrase itself, so no keyword is lost) and removing only the false question framing. No second model call, so no wasted latency either (the retry-based attempt cost a full extra ~11-13s generation for nothing). Verified: the real case no longer inverts, the mechanical rewrite reads correctly, and a full before/after run of all 15 eval cases is byte-identical everywhere except this one (only its compression % moved, from the reworded opener; retention unchanged, meaning unchanged from "fixed").

### Review-card open latency: investigated, partially fixed, real bottleneck identified
Real ask: clicking the badge felt ~0.5s slow to pop the card open. Reproduced and measured with cProfile (not assumed): `SuggestionPopup._new_window()` was destroying the ENTIRE Toplevel (header logo, wordmark, close/gear/theme icons, "on your device" pill — ~15 widgets, including a fresh disk read + PIL resize of the logo PNG) and rebuilding it from scratch on literally every open, even though the header is byte-identical between opens whenever the theme hasn't changed. Steady-state: ~400-440ms per open.

**Fix shipped: window pooling.** `dismiss()` now hides (`withdraw()`) the Toplevel instead of destroying it, keeping it in `self._pool`; `_new_window()` reuses the pooled window when its recorded palette signature (`self._pool_theme_sig`, a `(theme_setting, resolved_dark_bool)` tuple) still matches the current one, only clearing and rebuilding the BODY (destroy-and-recreate the one `_body` frame in a single call, not a Python loop over each child — the loop version was measurably slower, native recursive destroy on the whole frame beats N individual `.destroy()` calls). A real theme change is caught automatically by the signature mismatch (no special-casing needed): `retheme()` already calls `_apply_card_palette()` before forcing a rebuild, so the OLD pooled window's signature no longer matches and it's correctly discarded rather than reused stale. `self.window` itself still goes back to `None` on every dismiss exactly as before, so every one of the ~13 "is the card open" checks elsewhere in `main.py` is completely unaffected — this is purely an internal reuse detail. Verified: no widget bleed-through across different card states (loading→error→suggestions), theme-change still forces a real rebuild (confirmed via a different window object after a theme flip).

**Measured result: real but small.** The header-reuse win (fewer Tcl calls, no repeated disk+PIL logo reload) was confirmed in the profiler, but repeated timed runs came back statistically unchanged (~400-440ms before AND after) — the DOMINANT cost is rebuilding the suggestions list body itself (~40-50 widgets: fix rows, step headers, buttons) plus Tk's own paint pass, which happens regardless of header reuse since the content genuinely differs each open. The card already has incremental row-reuse logic for this exact problem (`_sync_fixrows`, used today only for LIVE-typing refreshes while the card stays open) that isn't applied to the initial open — that's the likely next lever, not attempted yet (bigger change: needs to handle genuinely different suggestion sets across a full close/reopen, not just growing the same list). One important caveat: this was measured by importing the app's source directly in a throwaway script (the "fresh" un-cached path used for measurement in general), not by clicking the real running exe, so it's a reasonable proxy but not the authoritative test.

### Grammar/punctuation fixes (found by deliberately testing odd punctuation)
All four verified with real true/false-positive test batteries before shipping, same standing discipline as every other rule in `suggestion_engine.py`.
1. **"Helloe" → "Helloed" instead of "Hello".** Windows' own spellchecker (`winspell.check`) offers `['Helloed', 'Helloes', 'Hello']` for "Helloe" — Comprsly's own `_best_typo_candidate` re-ranking exists specifically to override Windows' sometimes-odd order, but "Hello" and "Helloed" tied exactly (`_typo_distance` scores a trailing-letter deletion and a trailing-letter insertion the same), so the tie fell through to a "prefer the everyday word" tie-break list that was built from function/grammar words (the "which" vs "witch" fix) and had never covered conversational greetings. 3. **"its already planned" wasn't corrected.** Same its→it's predicate-word mechanism as §10k's batch (an adverb can't follow a possessive determiner, so "its ADVERB" is unambiguous) — "already" fit the exact same safety argument as the adverbs already in the list (probably, actually, clearly, etc.) but was simply missing. Added.

## 10n. Comprsly auto-correcting its own name (2026-07-25, v0.9.53)

### Terminal detection consistency fix (found from a live bug report, screenshot-confirmed)

Antonio reported the badge showing suggestions and an active "compress" option with nothing typed in a terminal. Root cause: `get_focused_text()` computed `is_terminal` from `GetForegroundWindow()` — a SEPARATE query from the `control` it was about to read text from. ## 10u. Button repaint glitch + a major terminal-read performance fix (2026-07-27, later still)

Two real fixes, both found from live reports, both verified directly against the running app/real terminal before shipping, version 0.9.93.

### Button repaint glitch ("Dismiss" left a ghost "iss" fragment behind)

Antonio's screenshot showed a stray "iss" fragment floating next to the Step 1 "Dismiss" button right after clicking Apply, only on Step 1, never on Step 2. Root cause: `_busy_button`'s `_wrapped()` only called `btn.update_idletasks()` on the ONE button whose own text changed (e.g. "Apply 4 fixes" → "Fixing..."). Antonio reported Apply "taking a little long" for both the grammar-fix and AI-compression paths. Root-caused directly against the real running terminal, not guessed:

- The v0.9.90 rewrite (real UIA `TextPatternRange` line-unit navigation — `Move(TextUnit.Line, ...)`, `MoveEndpointByUnit(TextUnit.Character, N)`, `ExpandToEnclosingUnit(TextUnit.Line)`) was a genuinely correct fix for a real prior bug (Windows Terminal's `TermControl` doesn't reliably include `\n`/`\r` characters in its text output at all, confirmed live: a 5507-character real read had zero of either). - **The actual fix:** the border rows are made of a distinctive, searchable character pattern (a run of 10+ U+2500 box-drawing characters), not a line concept at all — finding them is a plain regex search over the text already fetched by the single, separately-confirmed-fast `GetText(-1)` call (~0.001s regardless of buffer size), needing zero further UIA calls. This is immune to the original "`\n` unreliable" bug for the same underlying reason the UIA-navigation version was: it never assumes newlines exist either. `_extract_terminal_input_line` rewritten to search for the nearest border run before the marker (within a generous proximity gap, confirming "border, marker" structure the same way the old "is the line above a border" check did) and the nearest border run after it (the bottom edge, searched within a character-based cap equivalent to the old row-based `MAX_TERMINAL_WRAPPED_ROWS`), joining whatever's between them with collapsed whitespace. Same fail-closed behavior preserved throughout: no marker, no nearby top border, or no bottom border found within the cap all still return `None`, exactly as before.
- **Verified, not assumed:** timed directly against the real terminal after the rewrite — 0.003-0.056s per call, down from ~3.0s, and a 6-case synthetic test (empty input, short input, no marker, stray marker character far from any border, multi-row wrapped input with no real newlines — the exact original bug case — and a marker too far from any border to be trusted) all passed before shipping.
- `_log_terminal_extraction`'s docstring updated to reflect this is the SECOND rewrite of the same-day (first: string-split → UIA line navigation, for correctness; second: UIA line navigation → regex, for speed, keeping the same correctness guarantee) so a future reader doesn't have to rediscover this history from scratch.

### Partner Center upload: real automation gotchas worth knowing for any future session touching this UI

- **The trailer video's own "Upload" button opens a native OS file picker with no accessible DOM `<input type=file>` behind it** — confirmed by trying (`find` only ever located the button itself, never a file input; `file_upload` against the button errored "Element is not a file input"). This is the same class of limitation this file already documents for the >10MB package-upload case and Gmail's "Send mail as" popup — **not automatable from this environment, has to be done by the user directly.** Antonio uploaded the trailer + thumbnail himself; this session then only added the thumbnail's caption (Partner Center enforces a required caption/title on the thumbnail before it'll save — a real, live validation block, not optional) and picked the trailer as the "top of listing" selection.
- **Screenshot upload tiles, by contrast, ARE real `<input type=file>` elements and genuinely automatable** — but only reliably one file per upload call, with a fresh DOM check between each. A batched 5-file `file_upload` call reported all 5 as "uploaded" but only the first actually landed. Worse: reusing a `find`-returned element ref from before a page update silently **overwrote the wrong existing tile's image** (twice) instead of landing in the intended new empty "+" tile — caught only by screenshot-verifying after every single upload, not by trusting the tool's success message. What actually worked reliably: `read_page` on the specific tabpanel container after each upload, using the plain structural rule that the trailing `<button type="file">` with no `<image>` sibling immediately before it is the real next-empty-tile, re-derived fresh every time rather than reused.
- **The "Choose a trailer to play at the top of your Store listing" control is a custom Angular `he-select` web component, not a native `<select>`** — clicking it plus arrow-key navigation didn't reliably register a selection through browser automation (and this specific page also had frequent, unrelated blank/black-screenshot rendering glitches on large scroll jumps — small single-tick scroll nudges reliably fixed the repaint, worth knowing if this symptom recurs). What did work: reading the component's real DOM/property structure directly via JS (`document.querySelectorAll('he-select')`, inspecting its `he-option` children for the target's `value` attribute), then setting the component's own `.value` property directly and dispatching real `input`/`change` events — the component picked it up correctly, confirmed by the visible label updating and the page's own "Store listings: Updated" status flag after Save.
- **Certification-timing question came up directly — researched against real Microsoft documentation, not assumed:** listing-only submissions (no package change) skip the package security scan and Windows App Certification Kit testing entirely, since there's no binary to test — only a lightweight content/policy review runs. Per Microsoft's own 2018 Windows Developer Blog post on publishing times and the current Store-policy docs, this typically completes in **under an hour** once reviewed, meaningfully faster than the generic "up to 3 business days" ceiling that applies to submissions with a new package.
