## What changed, by fix

All in `Ventures/Comprsly/desktop/`.

### 1. ChatGPT / Gemini badge position (`main.py`)
Previously docked at a fixed pixel inset from the box's widened right edge — confirmed via live screenshots that this still landed on/near the mic icon on both sites (a fixed inset can't work reliably since the toolbar cluster's width differs by site). Replaced with real UI-tree detection:
- `_toolbar_cluster_left(control, raw_right)` walks the ancestor chain to find the toolbar row, then walks its children for real interactive controls (`_TOOLBAR_CONTROL_TYPES`) positioned right of the text area, returns the leftmost one's `.left`.
- `_BadgeRect` gained an optional `toolbar_left` field; `_position_for` docks there (`BADGE_TOOLBAR_GAP` = 10px gap) when found, falling back to the old inset math (`BADGE_INSIDE_INSET_OVERRIDES`) when it isn't.
- Wired into `watch_loop` with its own tick-to-tick cache (`toolbar_left_cache_key/val`), same pattern as the existing `box_right_cache_*`.
- **Not yet visually confirmed** — same structural limitation as every prior badge-position fix in this project (browser automation can't screenshot a separately-overlaid native window). Needs an actual look once installed.

### 2. Copilot / Perplexity badge position (`main.py`)
Real `debug.log` data pulled today showed their detected input box is genuinely short (Perplexity 53px tall, Copilot 27px tall) — far less than the full visual card including the toolbar row stacked below it, so vertical centering was landing near the top, overlapping the rounded border (confirmed via Antonio's own screenshots).
- `_input_box_bottom(control, raw_bottom)` — mirrors `_input_box_right`, widens the BOTTOM edge instead, gated on horizontal overlap (same column) instead of vertical (same row), since here the extra toolbar is stacked below, not beside.
- `BADGE_WIDEN_DOWN_SITES = {"Perplexity", "Copilot"}`, wired into `watch_loop` the same caching way (`box_bottom_cache_key/val`).
- Also **not yet visually confirmed.**

### 3. Badge showing up on non-chat pages (`main.py`)
Confirmed live: the badge anchored onto a slider thumb on an unrelated claude.ai Artifact page. Root cause: `app_label_for` only answers "which site is this" (domain/title match), nothing ever checked "what's actually focused." Fix: `_NEVER_A_COMPOSER_CONTROL_TYPES` denylist (sliders, buttons, checkboxes, tabs, toolbars, etc.) — the existing whole-page-`DocumentControl` rejection in `watch_loop` (the Google-New-Tab fix) now also rejects any of these types, falling through to the last good box position instead of jumping to whatever unrelated control just got focus. Domain-agnostic, covers every site.

### 4. Gemini Chrome side-panel detection (`main.py`)
Badge never showed in Gemini's docked Chrome side panel — a side panel never repaints the tab's own title, so neither existing signal (title match, URL/domain match) could ever see it. Real `debug.log` data from today showed the side panel's focused control reports `Name='Gemini Chrome :: New Conversation'` even while the tab title stays "New Tab." Added `_side_panel_label_for(hwnd)` / `KNOWN_SIDE_PANEL_NAME_PREFIXES` as a third signal (a control's accessible Name), consulted last in `app_label_for`'s browser branch, after title and domain both come up empty. Once matched it returns `"Gemini"`, so it flows through the exact same toolbar-cluster-left fix as the main tab (untested combination, flag if it looks off).

### 5. "Launch on login" toggle removed (`main.py`, `webui.py`, `webui/settings.html`)
Antonio confirmed it doesn't work on the Store/MSIX download. Working theory going in was a missing `<desktop:StartupTask>` manifest declaration — **worth double-checking, not fully confirmed:** `Build.md` §10x's own record of the last locally-verified package shows `windows.startupTask` WAS present with the correct `TaskId` and `Enabled="false"`, which contradicts a simple "never declared" theory. The actual root cause (Windows requiring separate user consent via Settings > Apps > Startup for a StartupTask, a signing-identity mismatch, or something else) was never chased down — Antonio's call was to just remove the toggle rather than debug it further. If you want to actually fix startup-on-login properly later rather than leave it removed, that root cause still needs real investigation, not another guess.
- Removed: the card/toggle in `webui/settings.html` (`General` page), its JS wiring (`data-launch`, the `set_launch` branch in the click handler), the `launch_on_login` key from `get_state()`'s response, and the `Bridge.set_launch` method in `webui.py`.
- Removed from the Tk fallback's `_render_general` in `main.py` too, along with a second piece of confirmed-dead code found alongside it: a "Badge position: Reset" button referencing drag-to-pin, which was removed from the *web* Settings back on 2026-07-25 when dragging itself was removed (2026-07-23) — the Tk fallback had just drifted out of sync until now.
- **Kept, deliberately:** `set_launch_on_login`, `launch_on_login_is_active`, `heal_launch_on_login`, the Run-key/StartupTask backend in `main.py` — still needed for any existing *unpackaged* (Inno Setup) install that already had this turned on. Only the UI surface is gone.

## Packaging steps (per `Build.md` §10x, the only process actually proven to work)

1. Rebuild the frozen exe (PyInstaller) with the version-bumped files above.
2. `MsixPackagingTool.exe create-package --template msix-conversion-template-generated.xml -v` — found at `%LOCALAPPDATA%\Microsoft\WindowsApps\MsixPackagingTool.exe`. **Requires an elevated (Administrator) terminal** — this needs Antonio to run it, not a Claude Code shell (no way to accept the UAC prompt). `SaveLocation` should point at `C:\ComprslyBuild\`, not the OneDrive-synced desktop path.
3. This produces a package with `<Description>None</Description>` and no `windows.startupTask` extension (the CLI template schema doesn't support those fields) — the GUI **Package Editor** step is still required on top, same as every prior round: open the generated package, fix the description, re-save, sign.
   - The `windows.startupTask` extension can be left in or dropped now that the login toggle is gone — either is fine, it's simply unused going forward either way.
4. **Known quirk, already accepted as normal (Antonio, explicit: "I don't want it any less or more until the next build"):** Package Editor's save auto-bumps the manifest's 4th version segment by 1 regardless of the source template's version — e.g. a `1.0.2.0` template routinely comes out as `1.0.3.0` after the Package Editor save. Don't fight this, don't try to force an exact final number, just note whatever it actually lands on.
5. Verify before calling it done, same chain as last time:
   - Extract `Comprsly.exe` from inside the `.msix`, SHA256-hash it, compare against the freshly-built `dist/Comprsly.exe` — must match exactly.
   - Extract and read `AppxManifest.xml` directly, confirm the `Description` and `Version` actually look right, not assumed.
   - `Add-AppxPackage -Path "..."` locally, confirm it installs and launches clean (`debug.log` shows no errors on startup).
